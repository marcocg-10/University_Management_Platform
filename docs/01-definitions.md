# 1. Definitions, Acronyms, and Abbreviations

## 1.1 Definitions
1. **Test-Driven Development**: technique used in software development where automated tests are created before implementing functional code. 
2. **Acceptance Criteria**: all the conditions that a product, user story, or increment of work must satisfy to be complete. They’re a set of clear, concise, and testable statements that focus on providing positive customer results. Acceptance criteria don’t focus on how you reach a solution but rather on the final desired outcome of the task.
3. **User Story**: a short, simple description of a feature told from the perspective of the person who desires the new capability, usually a user or customer of the system. User stories typically follow a simple template: "As a [type of user], I want [an action] so that [a benefit/a value]".
4. **Epic**: a large body of work that can be broken down into a number of smaller tasks (user stories). Epics often encompass multiple teams, projects, and even releases.
5. **Module**: a self-contained component or unit of a system that encapsulates a specific functionality or set of related functionalities. Modules are designed to be independent and reusable, allowing for easier maintenance, testing, and integration within larger systems.
6. **Product Backlog Item**: an item in the product backlog that represents a feature, enhancement, bug fix, or other work that needs to be done to deliver a product. PBIs are typically written in the form of user stories and include acceptance criteria to define when the item is considered complete.
7. **Definition of Done**: a shared understanding among the team of what it means for work to be considered complete. The DoD typically includes criteria such as code being written, tested, reviewed, and documented, as well as any necessary approvals or sign-offs.
7. **Continuous Integration**: a software development practice where developers frequently integrate their code changes into a shared repository, often multiple times a day. Each integration is automatically verified by running tests and builds to detect errors early and ensure that the codebase remains stable.
8. **Domain-Driven Design**: an approach to software development that emphasizes collaboration between technical and domain experts to create a shared understanding of the problem domain. DDD focuses on modeling the domain using concepts such as entities, value objects, aggregates, and repositories to create a rich and expressive domain model that reflects the business requirements.
9. **Pair Programming**: two people share a computer/space in which they work on a project. One is the driver, who writes the code, while the other is the navigator, who reviews each line of code as it is typed in. The two programmers switch roles frequently.
10.**Spike**: a timeboxed investigation or experiment carried out to reduce uncertainty in a user story or technical challenge. A spike may involve research, prototyping, or exploring different approaches.

- **DB**: Database
- **DDD**: Domain-Driven Design
- **DoD**: Definition of Done
- **LMS**: Learning Management System

- **TDD**: Test-Driven Development
